### 5.1.2 何时进入极致优化

```

    ↓

```

### 5.1.3 极致优化原则

| 原则 | 说明 |
|------|------|
| **每次只改一层** | 控制变量，确保可归因 |
| **从底向上** | L0 → L1 → L2 → L3 → L4，先优化指令再优化调度 |
| **负结果同样记录** | 失败的尝试也有价值，避免重复踩坑 |
| **闭环验证** | 每次优化后重新 msprof 采集对比 |

## 5.2 L0：指令级优化

> 前置引用：SIMD MicroAPI 签名 → 详见第 2 篇 § 2.7；SimdVF/SimtVF 执行模型 → 详见第 2 篇 § 2.6

### 5.2.1 SIMD 指令融合

#### vld2 去交错加载

**原理**：`vld2` 一次加载 256 bf16 → 两个 128-lane，替代两次 `vld`

```python
# 优化前：两次 vld
S.vld(vreg1, ub[0:128])       # 加载前 128
S.vld(vreg2, ub[128:256])     # 加载后 128
# VEC 指令数：2

# 优化后：一次 vld2
S.vld2(vreg1, vreg2, ub[0:256])  # 交错加载 256 bf16
# VEC 指令数：1
```

**实测**：per_token_cast g32 reduce，vld2+vcgmax 将 VEC ratio 从 97.6% 降至 72%

#### vand 替代 vabs

**原理**：位运算清除符号位 `0x7FFF`，比 `vabs` 少一条指令

```python
# 优化前：vabs
S.vabs(vreg_abs, vreg)        # 取绝对值

# 优化后：vand
S.vand(vreg_abs, vreg, 0x7FFF)  # 位运算清符号位
# 省一条指令
```

#### vmula FMA

**原理**：`dst = dst + src0 * src1` 融合乘加，减少寄存器往返

```python
# 优化前：vmul + vadd
S.vmul(temp, a, b)
S.vadd(dst, dst, temp)

# 优化后：vmula
S.vmula(dst, a, b)            # dst = dst + a * b
```

#### vexpdif 融合

**原理**：`exp(src0 - src1)` 融合减法+指数，Flash Attention softmax 关键优化

```python
# 优化前：vsub + vexp
S.vsub(temp, x, max_val)
S.vexp(result, temp)

# 优化后：vexpdif
S.vexpdif(result, x, max_val)  # exp(x - max_val)
```

### 5.2.2 寄存器复用策略

#### alloc_fragment 缓存中间值

```python
# 优化前：中间值存 UB，需往返
S.vsts(ub_temp, vreg)         # 存到 UB
# ... 其他计算
S.vld(vreg, ub_temp)          # 从 UB 重新加载

# 优化后：留在 fragment
frag = T.alloc_fragment((128,), dtype)
# frag 始终在寄存器中，零延迟访问
```

#### alloc_reducer + finalize_reducer

**原理**：硬件级 warp 归约，远快于软件归约

```python
# RMSNorm 核心：sum(x^2) 从寄存器直接归约
sum_sq = T.alloc_reducer((1,), "float32", op="sum", replication="all")
T.clear(sum_sq)
for i in T.Parallel(TILE):
    sum_sq[0] += x_frag[i] * x_frag[i]   # 从 fragment 直接归约
T.finalize_reducer(sum_sq)                # 硬件级归约
```

#### Fragment trick

**原理**：float4 分块利用寄存器级并行

```python
# RMSNorm d=7168 达 88%+ 带宽
x_frag = T.alloc_fragment((TILE,), "float32")
for i in T.Parallel(TILE):
    x_frag[i] = x_ub[i]        # 加载到寄存器
# 归约、rstd、输出全部从 x_frag 读写，无 UB 往返
```

### 5.2.3 dist 模式选择

#### 加载 dist

| dist | 说明 | 适用场景 |
|------|------|---------|
| `NORM` | 正常加载 | 连续数据 |
| `BRC_` | 广播 | 标量广播到所有 lane |
| `E2B_` | 每 8 元素广播 | per_token_cast inverse scale |
| `UNPK_B16` | bf16 解包 | bf16 → fp32 |
| `DINTLV_B16` | 去交错 | vld2 配套 |

#### 存储 dist

| dist | 说明 | 适用场景 |
|------|------|---------|
| `NORM_B32` | 正常存储 32B | 连续数据 |
| `ONEPT_` | 单点存储 | 标量输出 |
| `PK4_` | 4 字节打包 | e4m3 打包 |
| `PK_` | 通用打包 | 通用打包 |

**选择指南**：按数据布局和目标精度选择最优 dist，减少额外转换指令

### 5.2.4 SimdVF vs SimtVF 深度选择策略

| 维度 | SimdVF | SimtVF |
|------|--------|--------|
| 编程模型 | 向量寄存器 SIMD | SIMT 线程并行 |
| 线程概念 | 无 | 有（threads 参数） |
| 访问模式 | 规则连续 | 不规则 |
| 分支逻辑 | 无 | 支持 if-else |
| 归约 | vcmax/vcadd 高效 | 需软件归约 |
| 适用算子 | 归约/cast/softmax | gather/scatter |

**关键判据**：
- 访存模式是否规则？规则 → SimdVF，不规则 → SimtVF
- 数据量是否适合单核 256KB UB？适合 → SimdVF，不适合 → SimtVF 多核
- 是否需要线程级分支？需要 → SimtVF

## 5.3 L1：内存层级策略

> 前置引用：T.copy 参数 → 详见第 2 篇 § 2.4；InsertNd2Nz pass → 详见第 3 篇 § 3.3.2

### 5.3.1 L2 缓存控制

#### 策略选项

| `l2_cache_ctrl` | 说明 | 适用场景 |
|------------------|------|---------|
| `"NORMAL_FV"` (默认 load) | 正常 L2 分配 | 数据复用场景 |
| `"NOTALLOC_KEEP"` (默认 store) | 旁路 L2 流式访问 | 一次性大数据（减少 L2 thrash） |
| `"NOTALLOC_CLEAN"` | 旁路 + 清除 L2 行 | 避免污染后续访问 |
| `"NOTALLOC_PW"` | 部分写策略 | 部分写场景 |

#### 决策树

```
数据是否会被后续访问复用？
    ├─ 是 → NORMAL_FV（让 L2 缓存）
    └─ 否 → NOTALLOC_KEEP（旁路 L2）
        └─ 是否会污染后续访问？
            ├─ 是 → NOTALLOC_CLEAN
            └─ 否 → NOTALLOC_KEEP
```

#### 实测案例

```python
# per_token_cast: 64 核同时加载 32KB tiles → L2 thrash
T.copy(gm_a[...], shared, l2_cache_ctrl="NOTALLOC_KEEP")  # 旁路 L2
```

#### 负结果

```python
# per_token_cast L2 bypass 实验
T.copy(gm_a[...], shared, l2_cache_ctrl="NOTALLOC_KEEP")
# 结果：中性（性能无变化），但编译时间 10x 慢
# 原因：L2 非瓶颈（MTE2 才是瓶颈），旁路无收益
# 教训：L2 策略仅在 L2 命中率低时有效
```

#### 背景

Ascend Cube 引擎要求 **NZ（紧凑非零）布局**，但输入通常是 **ND（密集行主序）**。

#### InsertNd2Nz pass（自动）

> 原理 → 详见第 3 篇 § 3.3.2

```python
# 自动检测 UB(ND)→L1(NZ) 的 T.copy，重写为：
# scatter (ND → NZ 分散写) + post_copy (NZ → L1)
# 用户无需手动处理
```

#### 手动优化（预打包 NZ）


**Flash Attention 关键**：softmax 输出必须 NZ 布局才能喂给第二次 GEMM（PV）

### 5.3.3 Bank Conflict 消除

#### 诊断

```python
# msprof 检查
# aiv_vec_total_cflt_ratio > 5% → 存在 bank conflict
```

#### aswt_swizzle

**原理**：CUTLASS 风格 swizzle 重排 L1 访问顺序，消除 bank conflict

```python
@T.macro
def aswt_swizzle(tile_idx):
    # 奇数行反向遍历，打破规律性访问
    if row_idx % 2 != 0:
        n_tile = N_TILES - 1 - n_tile
    return m_tile, n_tile
```

#### UB 布局调整

```python
# 修改 alloc_shared shape/padding 改变 bank 映射

```

#### 实测案例

```python

# Cube 利用率显著提升
```

### 5.4.2 FixPipe 重叠

#### unit_flag_ctrl 参数

| 值 | 含义 | 适用帧 |
|----|------|-------|
| `0` (UF_NONE) | 不重叠 | — |
| `2` (UF_2) | 中间帧 FixPipe 重叠 | `kt = 0..K_TILES-2` |
| `3` (UF_3) | 尾帧 FixPipe 重叠 | `kt = K_TILES-1` |

#### 原理

FixPipe 是 Cube 后处理（类型转换 + 饱和），与下一轮 GEMM 重叠：

```
时间轴:  ──────────────────────────→
Cube:    [GEMM k=0] [GEMM k=1] [GEMM k=2]
FixPipe:        [FP k=0] [FP k=1] [FP k=2]
                                    ↑ 重叠
```

#### 代码示例

```python
T.gemm(a, b, c,
       clear_accum=(kt == 0),
       unit_flag_ctrl=T.Select(kt == K_TILES-1, UF_3, UF_2))
# 中间帧用 UF_2 重叠，尾帧用 UF_3 重叠
```

#### 实测案例

```python
# GEMM unit_flag_ctrl 将 FixPipe 与 MAD 重叠
# Cube 利用率从 60% 提升到 80%+
```

## 5.5 L3：流水线深度调度

> 前置引用：T.Parallel / T.Persistent / T.Pipelined → 详见第 2 篇 § 2.3

### 5.5.1 num_stages 调优

#### 原理

多缓冲流水：N 级流水有 N 份 buffer 在途

```
num_stages=2 (双缓冲):
  MTE2: [load k=0] [load k=1] [load k=2]
  VEC:          [calc k=0] [calc k=1] [calc k=2]

num_stages=3 (三缓冲):
  MTE2: [load k=0] [load k=1] [load k=2]
  VEC:          [calc k=0] [calc k=1]
  MTE3:                  [store k=0] [store k=1]
```

#### 选择策略

| num_stages | 说明 | 适用场景 |
|-----------|------|---------|
| 2 | 基础双缓冲 | MTE2/MTE3 重叠 |
| 3~4 | 深度流水 | 隐藏 HBM 延迟（Ascend 常用） |
| 6+ | 极深流水 | 需大 UB 容量支撑 |

#### UB 容量约束

```python
# 约束公式
block_m × block_k × dtype_size × num_stages ≤ UB_budget
# 例: 128 × 256 × 2 (bf16) × 4 = 256KB ≤ 256KB (刚好)
```

#### 实测对比

```python
# per_token_cast g32 实测
# num_stages=2: 带宽 55%
# num_stages=3: 带宽 62%
# num_stages=4: 带宽 66% ← 最优
# num_stages=5: 带宽 64% (UB 不足，spill)
# num_stages=8: 带宽 58% (严重 spill)
```

### 5.5.2 enable_offset 流水偏移

```python
# T.Pipelined annotations={"enable_offset": True}
# 同 pipe 任务跨迭代错开，减少资源争用
for kt in T.Pipelined(K_TILES, num_stages=3,
                       annotations={"enable_offset": True}):
    ...
```

**适用场景**：多任务流水（MTE2+VEC+MTE3）资源冲突时

### 5.5.3 T.Persistent 工作窃取

#### group_size 参数

| group_size | 说明 | 适用场景 |
|-----------|------|---------|
| 1 | 每核 1 tile，最细粒度 | 大 tile，负载不均衡 |
| 8 (默认) | 每核 8 tiles，减少调度开销 | 小 tile，调度开销显著 |

#### 实测

```python

# group_size=1: 带宽 66% ← 最优（大 tile 时调度开销可忽略）
# group_size=2: 带宽 65% (中性偏回退)
```

#### 负结果

```python

# 结果：中性偏回退
# 原因：大 tile 时工作窃取无益，反而增加调度开销
# 教训：大 tile 用 group_size=1，小 tile 用默认 8
```

```python
# 减少 UB 碎片，允许更大 tile
```

## 5.7 跨层组合优化

> 真实场景中，单一层级优化往往不够，需要跨层组合。

### 5.7.1 L0+L1 组合：Gather 优化

```
瓶颈：Vector 标量读（L0）+ L2 thrash（L1）

组合策略：
  L0: vld2 去交错加载（减少 VEC 指令数）
  L0: T.copy DMA 替换标量读
  L1: NOTALLOC_KEEP 旁路 L2

实测：d=128 从 296us(11%) → 87us(39%), 3.4x 加速
```

### 5.7.2 L1+L2+L3 组合：GEMM 优化

```
瓶颈：bank conflict（L1）+ FixPipe 未重叠（L2）+ MTE2 延迟（L3）

组合策略：
  L1: aswt_swizzle 消除 bank conflict
  L2: unit_flag_ctrl FixPipe 重叠
  L3: num_stages=3 K 维流水

实测：Cube 利用率 80%+
```

### 5.7.3 L0+L3+L4 组合：RMSNorm 优化

```
瓶颈：寄存器往返（L0）+ 归约延迟（L3）+ UB 分配（L4）

组合策略：
  L0: Fragment trick + alloc_reducer
  L3: double buffer (num_stages=2)
  L4: UB merge

实测：d=7168 达 1400+ GB/s (88%+)
```

### 5.7.4 跨层组合决策表

| 瓶颈组合 | 优化组合 | 预期效果 |
|---------|---------|---------|
| VEC + L2 thrash | L0 指令融合 + L1 L2 旁路 | 3x+ |
| bank conflict + FixPipe + MTE2 | L1 swizzle + L2 flag_ctrl + L3 stages | 80%+ Cube |
| 寄存器往返 + 归约 + UB | L0 fragment + L3 buffer + L4 merge | 88%+ 带宽 |
| MTE2 极限 | 无法突破 | 识别并停止 |

### 5.8.1 优化历程（8 轮迭代）

| 轮次 | 优化内容 | 层级 | h4096 延迟 | 带宽 | 保留 |
|------|---------|------|-----------|------|------|
| 基线 | 无优化 | — | 201.9 us | 2019 GB/s (49%) | — |
| R1 | num_stages=3 col_major | L3 | — | — | ✅ |
| R2 | UB-aware num_sf_slots | L4 | — | — | ✅ |
| R3 | PassConfig (fast_math etc.) | L4 | — | — | ✅ |
| R4 | vand 替代 vabs | L0 | — | — | ✅ |
| R5 | 自适应 packed_row_block_k | L1 | — | — | ✅ |
| R6 | **vld2+vcgmax bf16 归约** | L0 | 151.1 us | 2693 GB/s (66%) | ✅ |
| R7 | num_stages=4 g32 | L3 | 151.1 us | 2693 GB/s (66%) | ✅ |
| R8 | 5 个尝试 | L0-L4 | 151.3 us | 2689 GB/s (66%) | ❌/✅ |

### 5.8.2 R6 详解：vld2+vcgmax bf16 归约（关键突破）

```python
# 优化前：两次 vld + vcmax
S.vld(vreg1, ub[0:128])        # 加载前 128 bf16
S.vld(vreg2, ub[128:256])      # 加载后 128 bf16
S.vcmax(amax1, vreg1)          # 归约前半
S.v)vcmax(amax2, vreg2)         # 归约后半
amax = max(amax1, amax2)       # 合并

# 优化后：vld2 + vcgmax
S.vld2(vreg1, vreg2, ub[0:256])  # 交错加载 256 bf16
S.vcgmax(amax, vreg1)            # 群归约
S.vcgmax(amax2, vreg2)
amax = max(amax, amax2)

# 效果：VEC ratio 97.6*6% → 72%，延迟 201.9us → 151.1us
```

### 5.8.3 R8 详解：5 个尝试全部回退

| 尝试 | 层级 | 结果 | 原因 |
|------|------|------|------|
| vld2 in quantize | L07 0 | ❌ 无效 | 瓶颈是延迟非指令数 |
| 融合 reduce+quantize | L0 | ❌ 回退 2% | MTE2 流量不变 |
| 32 cores | L2 | ❌ 回退 44% | 并行度减半远超单核带宽提升 |
| L2 bypass | L1 | ❌ 中性 | L2 非瓶颈，编译 10x 慢 |
| group_size=2 | L3 | ❌ 回退 | 大 tile 时工作窃取无益 |

### 5.8.4 瓶颈分析

```
msprof 8-CSV 分析：
  PipeUtilization:
    aiv_vec_ratio = 79%
    aiv_mte2_ratio = 97%     ← MTE2 占用最高
  ResourceConflictRatio:
    vec_wait_ratio = 82%
    mte2_wait_ratio = 97%    ← MTE2 等待最高
  Memory:
    GM_to_UB = 27 GB/s per core (峰值 64 GB/s, 42%)

结论：MTE2 97% 占用"用 + 97% 等待率 → HBM 带宽硬件极限
```

### 5.8.5 负结果价值

| 负结果 | 教训 |
|-------|------|
| vld2 in quantize | 不减少 HBM 总流量的优化无法突破 MTE2 瓶颈 |
| 融合 reduce+quantize | 减少 VEC 指令 36% 但 MTE2 流量不变 → 无效 |
| 32 cores | 并行度减半的代价远超单核带宽提升 |
| L2 bypass | L2 非瓶颈时旁路无收益，反而增加编译开销 |
| group_size=2 | 大 tile 时工作窃取增加调度开销无益 |

**核心教训**：**不减少 HBM 总流量的优化无法突破 MTE2 瓶颈**

### 5.8.6 NPU vs GPU 架构差异

```
NPU (66% 带宽)                    GPU (80-90% 带宽)
┌──────────────────┐              ┌──────────────────┐
│ GM → UB → Fragment│              │ GM → shared → reg │
│  A MTE2 DMA 中<中间层> │              │ cp.async 直连     │
│ 64 核共享 HBM 通道  │              │ 独立 HBM 通道     │
└──────────────────┘              └──────────────────┘
```

NPU 的 MTE2/UB 中间层和 64 核共享 HBM 通道是性能差距的根因。

## 5.11 小结

本篇系统介绍了 TileLang NPU 算子的极致优化方法论：

| 层级 | 核心技术 | 关键 API/Pass |
|------|---------|-------------|
| L0 | SIMD 融合 + 寄存器复用 | vld2/vand/vmula + alloc_fragment/reducer |
| L1 | L2 策略 + NZ 布局 + bank conflict | l2_cache_ctrl + aswt_swizzle |
| L2 | Cube+Vector + FixPipe 重叠 | T.MixedKernel + unit_flag_ctrl |
| L3 | 流水深度 + 工作窃取 | num_stages + group_size |
| L4 | Z3 + UB merge + reg level | TL_ENABLE_AUTO_SCHEDULE + MergeUBAllocations |

**核心结论**：
- 极致优化 = 5 层技术栈 × 瓶颈驱动 × 闭环验证
- 从 60% 到 90%+ 需要跨层组合优化
- 硬件极限（如 MTE2 HBM 带宽）不可突破，需识别并适时停止
- **不减少 HBM 总流量的优化无法突破 MTE2 瓶颈**
